# ModelicaGraph

Loaded when working in `ModelicaGraph/` or `ModelicaGraph.Tests/`. The repository-wide rules are in
the root `CLAUDE.md`; this file carries what is specific to the graph.

Directed graph for tracking file/model relationships, dependencies, external resources, and style
checking. One of the six assemblies whose public surface is tracked in `PublicAPI.*.txt`.

**After any change to `TypeResolver`, `ClassElementResolver` or `UnitResolver`, run the resolution
corpus by hand** — the `test-tooling` skill has the command.

## Key files

| File | Purpose |
|------|---------|
| `ModelicaGraph/DirectedGraph.cs` | Main graph structure |
| `ModelicaGraph/GraphBuilder.cs` | Loads libraries, analyzes dependencies |
| `ModelicaGraph/StyleChecking.cs` | Orchestrates all per-class style rule checks |
| `ModelicaGraph/StyleCheckingSettings.cs` | Persisted style/formatting settings, and the severity map every rule resolves through |
| `ModelicaGraph/RuleSettingsLayout.cs` | Where each rule is set in the settings dialog — held to `RuleCatalog` by a test |
| `ModelicaGraph/ClassSuppressions.cs` | The one read of a class's `__MLQT` directives, kept on the class |
| `ModelicaGraph/Analysis/GraphAnalysisRunner.cs` | Runs the whole-graph analyses (`IGraphAnalyzer`), stamps severities, applies suppression |
| `ModelicaGraph/Analysis/MetricsCalculator.cs` | Coverage/size figures and `CoverageMeasurer`, the per-class measurement |
| `ModelicaGraph/Analysis/CoverageDimensions.cs` | Which coverage dimensions apply — to a repository (`TrackedFor`) and to one class (`ForClass`) |

## Node types

- `FileNode` - Represents a Modelica file
- `ModelNode` - Represents a Modelica model with definition, dependencies, and `HasExperimentAnnotation` flag
- `ResourceFileNode` - Represents an external resource file
- `ResourceDirectoryNode` - Represents an external resource directory

External resources (data files, C libraries, images) are tracked as graph nodes — `ResourceFileNode`,
`ResourceDirectoryNode`, and a `ResourceEdge` linking a model to each with its metadata. The reference
types, the extraction passes and the External Resources page are in the `external-resources` skill.

```csharp
var graph = new DirectedGraph();
var fileNode = new FileNode("file1", "Models.mo");
var modelNode = new ModelNode("model1", "MyModel", modelicaCode);
graph.AddNode(fileNode);
graph.AddNode(modelNode);
graph.AddFileContainsModel("file1", "model1");
```

## Key classes

- `DirectedGraph` - Main graph structure with node/edge management. `DependenciesAnalyzed` is the single source of truth for whether `UsedModelIds`/`UsedByModelIds` are populated — never infer it by checking whether some model happens to have edges
- `GraphBuilder` (static) - Loads files (`LoadModelicaFile`, `LoadModelicaFiles`, `LoadModelicaDirectory`), analyzes dependencies (`AnalyzeDependenciesAsync`, `AnalyzeDependenciesForModelsAsync`). Model queries are instance methods on `DirectedGraph` (e.g. `GetModelsInFile`, `GetUsedModels`, `GetModelUsedBy`)
- `ExternalStubBuilder` - Turns `DocumentedClass` records into graph nodes by synthesizing a minimal Modelica declaration, so every parse-tree-based consumer resolves them unchanged. Nodes are flagged `ModelNode.IsExternalStub`: never reported on, never written
- `IReadOnlyClassSource` / `ReadOnlySourceLoader` / `ReadOnlySources` (`ReadOnlySources/`) - **The one way a read-only library comes in**, recovered from documentation or supplied from memory as Modelica text. Read-only is decided once per level: the class (`IsExternalStub`, set before it reaches the graph), the file (`ReadOnlySources.IsReadOnlyPath`: a `.moe`, or under `mlqt-readonly://`, never on disk — every write path asks it) and the library (`LoadedLibrary.IsReadOnly`). `ReadOnlySources.Precedence` is the one rank between copies of a class or library; `KindOf(node)` tells readable, supplied and recovered classes apart. See the `encrypted-libraries` skill
- `StyleChecking` / `StyleCheckingSettings` - Run configurable style checks on model definitions
- `StyleCheckingSettings` includes `FormattingExcludedModels` (models that skip the formatter and formatting-rule findings) and `SvnBranchDirectories` (configurable per-repository SVN branch directory names, default: trunk/branches/tags). `SeverityFor(id)` is the **only** way to ask what a rule will do — it resolves governors, prerequisites and formatter-derived levels, none of which are visible in the raw `RuleSeverities` map. `StampSeverities` is the one place configuration is applied to findings
- `ModelDefinition.Borrow` - **The convention for reading a class you do not own.** Parses if needed, runs the work, and releases the tree again *only if this call is what parsed it*. Read it before adding any `EnsureParsed()`: the two halves have come apart in both directions, and a walk that keeps a base class's tree accumulates over tens of thousands of classes. The bulk load pass in `GraphBuilder` is the deliberate exception, and says so
- `ClassSuppressions.For(definition, modelId)` - **The only read of a class's `__MLQT` directives.** A class-level `suppress` or `spelling` reaches **every class nested in the one carrying it** — one annotation on a package waives a rule for the sub-package, which is how Dymola's generated `_fmu` models are quieted. Inside one tree `SuppressionSet.IsSuppressed` sees the nesting itself; a class in a node of its own reaches its packages' directives through `ClassSuppressions.Enclosing(graph, id)`, which the checker (via `StyleCheckContext.EnclosingSuppressions`) and `GraphAnalysisRunner` both ask. Component-level waivers and `format=false`/`preserveOrder` stay with their own class. Three passes want the same answer about the same class in one run — the checker, the coverage measurer and the graph analyses — and each used to walk the tree for itself. Kept on the class as `SuppressionSet.Empty` when there is nothing, so a library of tens of thousands costs a reference each
- `ClassImports.For(definition)` - **The imports a class declares, read once and kept on the class.** Name lookup asks each *enclosing* class for its imports as well as the class's own - MSL declares `import Modelica.Units.SI;` once in `Modelica.Blocks` for every block below it - so a package is asked hundreds of times per run. `TypeResolver.ResolveName` is the one lookup, and dependency analysis's `ReferenceResolver` delegates to it; the two had drifted, and neither saw an enclosing package's imports (B292). **The innermost scope wins**: each scope's classes, then the classes it inherits, then its imports - qualified and alias imports before wildcards, whatever order they are written in (MLS §13.2.1) - from the class outward, and the name as written - matched at the root - last. **Only the first segment is looked up**; each later one is a member of the class before it, nested or through its bases (a short class's included), and once the first is bound the search is over - `Medium.ThermodynamicState` under `replaceable package Medium = PartialMedium` is `PartialMedium.ThermodynamicState`, and if that is not there the name means nothing rather than a package's own `Medium.ThermodynamicState` further out. `TypeResolver.ResolveNamePath` says how it got there: the class per segment and how the first was bound (`NameBinding` - own, inherited, import, alias, wildcard, root, global), which is what a rename or move asks. Trying the root first let a top-level `Constants` answer for `Lib.Constants`. Lookup **stops at an `encapsulated` class**, root included - which is why such a class imports what it uses - and `ClassImports.IsEncapsulated` answers that once per class, beside its imports. A leading dot is the one exception to all of it, and is passed as `global` because the callers strip it; the grammar keeps a type name's dot outside `name`, so `ReferenceResolver.GetQualifiedName` puts it back
- `FormattingExclusion.Excludes(model, settings)` - **The only answer to "must the formatter write this class back unchanged?"**, over both mechanisms: the `FormattingExcludedModels` name list and `__MLQT(format=false)` / `preserveOrder=true`. Asked per caller instead, the annotation reached the full library save and not the incremental format — the path that runs at startup and after every VCS operation — so the rename-safe mechanism the docs recommend was the one the formatter ignored. Note this is a **different question** from the one the checker and the dashboard ask: writing is per rendered definition (the renderer rewrites a class's whole source or none of it), reporting is per class (`SuppressionSet.PreservesFormatting`)

## `Analysis/` — the whole-graph half (phase 6)

- `IGraphAnalyzer` / `GraphAnalysisContext` / `GraphAnalysisRunner` - Analyses that need the graph rather than one class: `PackageOrderAnalyzer`, `UsesHygieneAnalyzer`, `UnusedClassAnalyzer`, `UnusedImportAnalyzer`, `UnusedMembersAnalyzer`, `ShadowingAnalyzer`, `UndeclaredNameAnalyzer`. `RequiresDependencyAnalysis(settings)` says whether the edges are needed first
- `UndeclaredNameAnalyzer` (`MLQT.Reference.Undeclared`) - **the roadmap's three-state rule in practice.** Every name a class uses comes from `ParserVisitors/NameUseCollector` (values, calls, types, bases, imports and modification targets, with annotations, named arguments and `for` iterators left out). It is resolved with `ComponentReferences`/`TypeResolver` and, where they miss, walked again segment by segment, to say which segment failed and **whether the miss could have been a hit**. It is reported only when every scope searched is complete: readable, all bases resolved, no unresolved import that could bind the name, every enclosing package loaded. A first segment found nowhere also has to be something no unloaded library could supply: a plain variable, or a name the library's `uses(...)` rules out. Anything reached through `replaceable` or `expandable` is never judged. Nested classes are found with `TypeResolver.MemberClass`, never in an interface, which holds only the classes written inline. A predefined type's attributes and an enumeration's literals are checked from their own lists. A tool's own functions and flags (`ModelicaParser/Helpers/ToolBuiltIns`) count as declared only for the tools in `StyleCheckingSettings.AcceptedToolBuiltIns`, and only where lookup did not resolve the whole name. A name it resolves in part is still the tool's: MSL has a `Modelica.Utilities.Strings.Advanced`, so under `import Modelica.Utilities.Strings.*` every `Advanced.Translation.X` flag bound to it and failed on `Translation`, while Dymola reads the flag regardless. Measured on 2026-10-25: nothing reported over MSL 4.1.0, `ModelicaTest` and Buildings, 99% of MSL's 200k name uses judged, and 4.6 s over Buildings' 7,510 classes
- `TypeResolver` / `ClassElementResolver` / `UnitResolver` - Inheritance- and import-aware resolution. They cache **the answer, not the tree**. **`TypeResolver.IsPredefined` is the language's list and nothing else** (MLS 3.7 §4.9): `Complex` was on it until 2026-10-25, which left every class built on it without members, `u.re` unresolved and the units on `re`/`im` unseen. It is the operator record of `Complex.mo` and resolves as any class does. The one place that still names it is `StyleChecking.CreateSimpleTypeLookup`, which keeps ordering a `Complex` declaration among the variables, as it always did, so Format All moves nothing. Measured: MSL and Buildings report the same findings, rule for rule, before and after. `UnitResolver.ResolveAttributes` gives the `unit`/`displayUnit`/`quantity` strings a type chain fixes (`UnitAttributes`, nearest definition winning per attribute), each link a short alias or a long-form `type` around one `extends` - the form a type with an `equalityConstraint` must take; `Resolve` is its yes/no view and shares its cache. `ResolveWithInheritance` adds a class's **ancestors' nested classes**, and nothing else of their scope: a base's packages and imports are not inherited (MLS §5.3.1, §13.2.1), so a name written in a base is resolved by asking with the base's id - which is what `ResolvedElement.OwnerId` is for. They are looked for **at each scope, after its own classes and before its imports and enclosing packages** - where Modelica looks - so a base's replaceable `Medium` wins over a package's own. Dependency analysis and the reference locator resolve that way too (`ReferenceResolver`); only the walk of a class's own bases (`DirectBases`) resolves an `extends` name differently, with `ResolveBase`: without the class's **own** inherited classes, which that clause is bringing in, and with the enclosing packages' - `P.M`'s `extends PartialThing` is `Q.PartialThing` when `P extends Q`. What a class extends is read once and kept on it (`ClassImports.BasesOf`), with its imports and `encapsulated` flag, so walking a chain costs no parse. Passing `null` imports means "read the class's own"; `[]` means none. `ClassElementResolver.ReferencesIn(graph, class, ...)` is the one way to ask what a component reference (`inertia1.flange_b.tau`, `shafts[2].phi`, `Modelica.Constants.pi`) names: the element per segment and the class the last one's type is, with subscripts dropped, protected members reachable only from the class itself, enclosing classes lending their constants only (and nothing past an `encapsulated` one), and class-qualified names looked up as the language does. Make one per class, pass it an `InterfaceCache` and an `AncestorCache`, and drop it when the class is done: it keeps that class's members for its own lifetime and puts only the types references pass through into the run's cache (B147). `ResolveReference` is the one-shot form. `ComponentReferences.Start` answers only where a reference starts - the class it goes through and how many segments name it, `Modelica.Constants` in `Modelica.Constants.pi`, `Types.Init` in an enumeration literal - and is what **dependency analysis and the reference locator** ask when a name is not a class by its whole name: before it, those uses linked to nothing, so the classes read as unused and a rename left them behind. A locator site carries the class each segment named and how the first was bound (`ReferenceSite.SegmentIds`, `FirstSegmentBinding`), and the moves that re-qualify references **leave a site as written while it still means its class** (`EditTools.StillMeansItsClass`): `Medium.State` under a base's replaceable `Medium` stays relative - the full name would fix it to the base's default and undo every `redeclare` - until the class it names leaves the base, and a name an import brings in stays because the import clause is re-qualified instead. A name whose leading segments go through a target and whose last does not (`Medium.State` where `Medium = Water`) is a site for those leading segments. `mlqt_refactor_class`'s rename targets the class **and every class inside it**, and rewrites the segment of each site that spells the old name (`EditTools.RenamedSegment`) - `Pkg` in `Pkg.State` and `Root.Pkg.State` - leaving a relative name inside the class, an alias's `P.State`, and an alias or local short class **that happens to share the class's name** as written - the first segment is renamed only where it was bound to the class. **Renaming a replaceable class renames every `redeclare` of it** (`ReferenceLocator.Redeclarations`): in an extends clause's, a component's or a short class's modification, nested ones included (`h(b(redeclare package Medium = W))`), and the body-level `redeclare package Medium` of each class extending it, with the names that class writes through its own. A redeclare can sit any number of modifications deep (`h(b(redeclare ...))` in a class that only uses `Holder`), so for a replaceable class every class reaching a derived one through its users is looked in, not only the direct users. **It refuses a new name that is already taken where a renamed reference is written** (`Analysis/NameCapture`): a reference starting with the new name is looked up from its own class outward, and a nearer class or component of that name would answer for it - the file parses and the reference silently means something else. The moves that write full names refuse the same way (`NameCapture.ForFullNames`): a full name starting with `Root` means something else where a class declares a `Root`, and nothing at all inside an `encapsulated` class - judged, for a reference inside the moving class, where it is going rather than where it was. An import clause is skipped by both checks: it is looked up from the top. **An `import` clause's name is global** (MLS §13.2.1), so dependency analysis and the locator resolve it from the top (`ReferenceResolver.GetReferenceName`); resolved from the class outward, an encapsulated class's imports linked to nothing. **A short class is an extends clause in all but syntax**: `Collect` lists `model R2 = Resistor(R = 2)`'s base's members with its modifications applied, and `DirectBases`/`BaseClasses` name its base - a diagram takes its components from one and its wiring and graphics from the other, so they must agree (B316), and `ResolvedElement.ModifiedIn` names the class a modified default is written in, which is where its names resolve. **So is a class extends** (`redeclare record extends ThermodynamicState`, which every medium uses): its base is not looked up as a name, which found the class itself, but is the class of that name its *enclosing* class inherits (MLS §7.3.1) - `ClassElementResolver.ResolveBaseOf`, which both `DirectBases` and `Collect` go through, so a medium's own `state.T` reaches `PartialMedium`'s
- `MetricsCalculator` / `CoverageMeasurer` - The dashboard's figures, and the per-class measurement the checker triggers while it still holds the tree
- `CoverageDimensions` - `TrackedFor(settings)` for a repository, `ForClass(...)` for one class. **`ForClass` is the single narrowing**: every way of taking a class out of scope (`ExcludedLibraries`, `FormattingExcludedModels`, `__MLQT(format=false)`) is asked there, because each arrived separately and each was taught to the checker before anything asked what it meant for the report
